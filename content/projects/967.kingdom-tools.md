## Engineering Overview

Kingdom Tools is a Kubernetes-native internal developer platform that extends the cluster with a custom resource definition (`KingdomService`) and a continuous reconciliation controller. It's not a dashboard layered on top of kubectl — it's a platform extension that defines how services are created, what infrastructure they own, and ensures declared state matches actual state.

The core workflow: declare a service as a KingdomService CR, `kubectl apply` it, and the controller provisions isolated infrastructure across nine data layers within seconds. If something drifts, the controller fixes it. If a resource is orphaned, the audit engine flags it.

On top of that platform, Kingdom Tools now runs the AI side of the lab: the three NVIDIA Jetsons (Nova, Echo, Charlie), the RTX 3090 training PC, and the models, datasets, benchmarks and experiments between them. It's where a model gets pulled, benchmarked, fine-tuned, graded, and deployed to an app — without opening an ssh session.

```yaml
apiVersion: kingdom.donavanjones.com/v1alpha1
kind: KingdomService
metadata:
  name: my-service
spec:
  template: ai-agent
```

```bash
$ kubectl get ks
NAME         TEMPLATE    PHASE   AGE
my-service   ai-agent    Ready   12s
```

## Technical Highlights

::HighlightGrid

::HighlightCard{icon="mdi:kubernetes" title="KingdomService CRD & Controller"}
Services are defined as Kubernetes custom resources with a structured spec (template, resources, deployment config) and a status subresource (phase, per-resource conditions, observedGeneration). A background controller thread watches all CRs via the Kubernetes watch API and continuously reconciles desired state to actual infrastructure across nine data layers.
::

::HighlightCard{icon="mdi:rocket-launch" title="Template-Based Provisioning"}
Ten service templates cover every workload type: web apps, AI agents, scrapers, API services, background workers, document stores, search services, event-driven services, workflow engines, and analytics pipelines. Apply a CR with a template name and the controller creates isolated resources with no manual steps.
::

::HighlightCard{icon="mdi:shield-search" title="Audit & Drift Detection"}
The audit engine cross-references every database, bucket, Redis slot, Weaviate collection, MongoDB database, OpenSearch index, Kafka topic, Temporal namespace, and ClickHouse database against the service catalog. Orphans and missing resources are flagged. The controller automatically fixes drift on the next reconcile cycle.
::

::HighlightCard{icon="mdi:sync" title="Continuous Reconciliation"}
The controller runs as a daemon thread inside the FastAPI process. It watches for CR changes, handles watch expiry with automatic relist, uses exponential backoff on errors, and tracks observedGeneration to skip already-reconciled services. Finalizers handle clean deletion.
::

::HighlightCard{icon="mdi:key-variant" title="Secrets Management"}
Per-service K8s Secrets (SECRET_KEY, JWT_SECRET, API_KEY) generated with cryptographically secure values. Add custom keys, rotate individual keys or all at once. Secrets are labeled `managed-by: kingdom-tools` and never displayed in the UI.
::

::HighlightCard{icon="mdi:chart-line" title="Grafana Dashboard Provisioning"}
One-click per-service Grafana dashboards with seven panels: request rate, error rate, p95 latency, memory usage, CPU usage, pod restarts, and a Loki log viewer. All panels scoped to the service's namespace and pod pattern.
::

## Apps & Starter Kits

An app is one record that holds everything it needs: a KingdomService for its infrastructure, an AI part (which model on which Jetson for chat, embeddings and vision, plus Kokoro TTS, Whisper STT and Dreamer images), and one combined `.env` stored as a Kubernetes secret and never committed.

Starter kits create a Gitea repo with a working app — Nuxt, Next, SvelteKit, Astro, PERN, MERN, MEVN, MEAN, RAG Chat, or FastAPI + HTMX. Every kit ships with Tailwind CSS v4, a chat panel wired to the app's model, a health endpoint, an ARM64 Dockerfile, Kubernetes manifests, and a Gitea Actions pipeline. A setup assistant turns a request like "an app with a database, storage and a chat model" into a validated plan.

## The AI Lab

::HighlightGrid

::HighlightCard{icon="mdi:chip" title="Devices"}
Manages the three Jetsons without ssh. Load and unload Ollama models, start and stop services through a device agent limited to a fixed list of systemd units, tune flash attention, KV cache and context, and pin a model so it stays loaded. Models are pulled from a catalog scored against each box's memory and disk, and kept on "shelves" — quant ladders from Q8 down to Q2. Setups apply a whole-lab state, like "vision experiment", in one click.
::

::HighlightCard{icon="mdi:speedometer" title="Benchmarks & Model Sweep"}
Each run loads a model cleanly, measures it, and puts the box back. Speed (load time, GPU offload, prompt and generation tokens/s), coding (HumanEval, run in a locked-down throwaway pod), and tool calling are stored in Postgres and run on every Jetson at once. The model sweep records which models really work on each box at which KV cache type and context.
::

::HighlightCard{icon="mdi:tune-variant" title="LoRA Lab"}
Datasets and training on the 3090 against the original Hugging Face weights. The output is a GGUF LoRA adapter Ollama can attach to any quant of the same family on any Jetson, so one run can be tested from Q8 to Q3 and scored against the base on its own test questions. It also trains Stable Diffusion 1.5 LoRAs and sends them straight to Dreamer.
::

::HighlightCard{icon="mdi:flask" title="Distillation & Model Builder"}
A big teacher writes a training set — SDXL for images, Ornith 35B for text and code (Python must parse) — and a small student learns it in the LoRA Lab. The Model Builder merges a finished LoRA into its base, or fully fine-tunes a model of 3B or smaller, into one standalone Q8_0 GGUF deployed to a Jetson. Model Records track every run's base, dataset fingerprint, settings, and score.
::

::HighlightCard{icon="mdi:test-tube" title="Sandboxes & MCP"}
Pick any model on a Jetson, tick the storage it gets — PostgreSQL, an Apache AGE graph, Redis, MinIO, Weaviate, MongoDB, knowledge bases — and chat with it, with every tool call shown. All of it starts empty and is removed with the sandbox. Each sandbox is also an MCP server, so Claude Code or any MCP client can use the same tools. Good chats can be saved as training data.
::

::HighlightCard{icon="mdi:book-search" title="Knowledge Bases & Crawler"}
Turns websites and dataset files into something models and apps can use. A polite crawler (robots.txt, per-host rate limits, round-robin across sites) collects pages to MinIO, chunks are embedded into a Weaviate class, and an Apache AGE graph links sources, documents, authors and topics. Bases are graded on test questions — retrieval hits, right answers, honest "the sources don't say", and real versus invented citations — with and without the graph. Apps get an OpenAI-compatible endpoint that answers from a base.
::

::HighlightCard{icon="mdi:code-braces" title="Code Search"}
Indexes Gitea repos by meaning and by exact name: source files are chunked, embedded on a Jetson and stored in Weaviate. Search links to the exact lines in Gitea, and Ask sends the top matches to a model that answers from them.
::

::HighlightCard{icon="mdi:robot-industrial" title="Robot Lab"}
Vision models run on Echo through the K3s NVIDIA runtime class. Clips and cameras feed pipelines like a conveyor counter (detect and track objects crossing a line), live model views, and single-camera depth. Detectors are trained on the 3090's robot trainer from Robot Lab clips and scored on footage they never saw.
::

::HighlightCard{icon="mdi:school" title="AI Training"}
A hands-on course from basics to robot learning, run in JupyterLab on the 3090: training loops, CNNs, a tiny GPT, LoRA fine-tuning, RAG, quantization and distillation, diffusion, PID and reinforcement learning, object detection, and LeRobot/SmolVLA. Every lesson ends with something that runs on a Jetson.
::

::HighlightCard{icon="mdi:console" title="Command Bar"}
Ctrl+K on any page. A LoRA fine-tuned model maps plain English to one of 15 actions. Checks run immediately; changes show a plan and only run after a click. The model never executes anything — its words are resolved to real ids first. Every request is logged and exported nightly as new training rows, so the command bar trains on its own usage.
::

## Inside the App

Each AI lab page below is shown as it runs on the cluster, followed by what it does and the jobs it handles.

### Devices

![Devices page: one-click setups and live memory, disk, load and temperature for each Jetson](/img/projects/kingdom-tools/devices.png)
*Whole-lab setups applied in one click, and live memory, disk, CPU/GPU load and temperature for each Jetson.*

The Devices page is the control panel for the three Jetson Orin Nanos — Nova (image generation), Echo (speech and vision) and Charlie (language models). Instead of an ssh session per box, it shows which models each one has and which are loaded, and lets you load, unload or pin them. It starts and stops services through a small device agent that can only touch a fixed list of systemd units. It also sets Ollama's flash attention, KV cache type and context size, and drops the page cache or scans the disk using a short-lived pod pinned to that node.

New models come from a catalog scored against each box's free memory and disk, so a model that won't fit is flagged before it's downloaded. Shelves keep quant ladders, Q8 down to Q2 from one quantizer, so the rungs can be compared fairly. **Setups** save a named state for the whole lab — which services run, which models are loaded, which Whisper model is live — and apply it in one click.

**Use it for:**
- Switching the lab between workloads, such as a "Baseline" day versus the STARNET crew game with Dreamer, Kokoro and Whisper
- Pulling a new model and seeing straight away whether it fits a box, and at which quant
- Watching memory and temperature during a long run before a box runs out of memory
- Giving an app its AI: an app's model and services are saved as a setup

The benchmark results from these boards are published as the [Jetson Orin Nano LLM leaderboard](/jetson-leaderboard), exported straight from the Kingdom Tools benchmark database.

### LoRA Lab

![LoRA Lab: datasets and training settings for a run on the 3090](/img/projects/kingdom-tools/lora.png)
*The RTX 3090 trainer online and idle, text and image datasets with their train/test splits, and a run's settings.*

The LoRA Lab is where models get customized. A dataset is imported from MinIO, split into train and test rows, and trained on the RTX 3090 against the original Hugging Face weights. The result is a GGUF LoRA adapter that Ollama attaches to any quant of the same model family on any Jetson. One training run can then be tested from Q8 down to Q3 to find the smallest model that still does the job.

After training, the Lab scores the base model and the tuned model on the dataset's own test questions, so every run comes with a before-and-after number. It also trains Stable Diffusion 1.5 LoRAs from captioned images. A trigger word teaches the style, the 3090 renders without-and-with comparisons at one seed, and **Send to Dreamer** copies the adapter to the Jetson that draws images.

**Use it for:**
- Teaching a small model a narrow skill, like the command bar's function calling, so it runs well on a Jetson
- Training an art style, like the pixel-art `kgdm_pixel16`, for the image generator
- Comparing one adapter across quants and boxes before deploying it

### Model Records

![Model Records: each LoRA run's base, dataset fingerprint and score from base to tuned](/img/projects/kingdom-tools/records.png)
*Every run's base model, dataset fingerprint and score. The command bar's Qwen3 0.6B went from 31.2 to 96.5 on its test questions.*

Model Records keeps one row per training run: the base model, the dataset by name, size and fingerprint, the settings, where it was deployed, and its score against the base. The fingerprint is kept with the run, so a record still says exactly what it was trained on after the dataset changes or is deleted. Scores come from each dataset's own test questions, so the page is built for comparing runs on the same dataset. It answers questions like "did v7 of the data actually beat v5?"

**Use it for:**
- Tracking how a model improves as its dataset grows (KingdomQwen1 → KingdomQwen7)
- Choosing between base models, here FunctionGemma 270M versus Qwen3 0.6B for tool calling
- Keeping an audit trail of what's deployed and how it was made

### Distillation

![Distillation: SDXL writes image examples for Stable Diffusion 1.5 to learn](/img/projects/kingdom-tools/distill.png)
*A big teacher writes the training set: SDXL generated 300 pixel-art examples for a Stable Diffusion 1.5 LoRA, and Ornith 35B is ready for text and code.*

Distillation solves the hardest part of fine-tuning: getting good training data. A large teacher model writes the examples, and a small student model learns them in the LoRA Lab. For images, SDXL draws a style across a list of subjects and variations, with optional snapping to a pixel grid and palette. For text and code, Ornith 35B writes the answers. Duplicates are dropped, and code must contain a code block whose Python parses.

Jobs join the 3090's single queue, which unloads Ornith (21 GB) before anything else needs the GPU. Results are previewed, then sent to the LoRA Lab as a dataset with one click.

**Use it for:**
- Giving Stable Diffusion 1.5 a style that only SDXL can draw well, so it runs on a Jetson
- Building a topic-specific text or coding dataset without writing it by hand
- Shrinking what a 35B model knows about a narrow task into a model small enough for the edge

### Sandbox

![Sandbox: chat with a Jetson model that has its own graph, cache and vector storage](/img/projects/kingdom-tools/sandbox.png)
*A model on a Jetson with its own throwaway storage, usable in the chat or over MCP.*

A sandbox is a safe place to see what a model does with real tools. Pick any base, LoRA or merged model on a Jetson, tick the storage it gets — PostgreSQL, an Apache AGE graph, Redis, MinIO, Weaviate, MongoDB, or read access to knowledge bases — and chat with it. Every tool call appears in the conversation with what the model sent and what came back. All the storage starts empty, is isolated to the sandbox, and is removed with it.

Each sandbox is also an MCP server with the same tools plus `ask_model`, so Claude Code or any MCP client can connect to it. **Save as training data** turns a good conversation into a LoRA Lab dataset.

**Use it for:**
- Testing whether a small model can really drive SQL, graph or vector tools before an app depends on it
- Giving an AI coding assistant a disposable database and file store to work against
- Collecting good tool-use transcripts to fine-tune the next model on

### Knowledge

![Knowledge: search and ask a knowledge base of 751,202 chunks with a graph of authors, sources and verses](/img/projects/kingdom-tools/knowledge.png)
*751,202 embedded chunks plus an Apache AGE graph of eras, topics, verses, authors, sources and documents.*

Knowledge turns websites and dataset files into something models and apps can search. A base has one source: a polite web crawl, a `.jsonl`/`.json`/`.parquet` file from MinIO, or an existing Weaviate collection. It is built in three durable steps: **collect** pages to MinIO, **embed** chunks into its own Weaviate class, and **graph** them into an Apache AGE graph of sources, documents, authors and topics. The Theology profile also adds eras, Bible verses, and which verses are cited together.

Search combines vector and keyword matching, removes duplicate passages, and lets the graph steer results toward the works and authors a question names. **Quality** grades a base on test questions: how often search finds the right source, right answers, honest "the sources don't say", and real versus made-up citations, each measured with and without the graph.

**Use it for:**
- Retrieval-augmented answers with citations, here across the Church Fathers corpus
- Giving an app a knowledge API (`search`, `related`, `ask`, and an OpenAI-compatible chat endpoint) without a database login
- Proving whether a knowledge graph actually improves answers, rather than assuming it

### Robot Lab

![Robot Lab: a conveyor-counting pipeline and YOLO models benchmarked on Echo](/img/projects/kingdom-tools/robot.png)
*A line-crossing counter pipeline, and YOLO models benchmarked on Echo (YOLO11 nano at 22.7 fps).*

The Robot Lab is for proving a robot idea before building the robot. Vision models run on Echo through the K3s NVIDIA runtime class, fed by uploaded clips or live cameras. Pipelines turn a model into a working rig: **count** objects crossing a line (detect and track), **view** a model's output live, or estimate **depth** from one camera.

The model table covers detection, segmentation, pose, open-vocabulary detection (YOLO-World, name what to find in words) and segment-anything. Each model is benchmarked alone over 50 frames for fps, latency and memory, so you can see what fits beside an LLM or speech model on the same 8 GB box. TensorRT engines are built on the box for its exact GPU and run 2–4× faster. Custom detectors are trained on the 3090 from Robot Lab clips and scored on footage they never saw.

**Use it for:**
- A conveyor counter or sorter, prototyped from a phone video before any hardware exists
- Choosing the smallest, fastest vision model a robot can afford
- Training a detector for your own objects and checking it holds up on new footage

### Datasets

![Datasets: browse and edit training datasets stored in MinIO](/img/projects/kingdom-tools/datasets.png)
*The image, LLM and speech datasets in MinIO, browsable and editable in place.*

Datasets is a file browser and editor for the training data in MinIO, organized by type: image, LLM (coding, function calling, instruction, retrieval and their evals) and speech. JSONL and JSON files are edited row by row, with a rolling backup on each save. Bigger files and Parquet are paged and searchable, with an extract to a smaller editable copy. Imports into the LoRA Lab are streamed, so multi-gigabyte files never sit in the pod's memory.

**Use it for:**
- Fixing bad rows in a training set without downloading it
- Sampling a slice of a large public dataset to fine-tune on
- Reviewing the command bar's nightly log export before it becomes training data

### AI Training

![AI Training: a three-level course of notebooks that run in JupyterLab on the 3090](/img/projects/kingdom-tools/study.png)
*Basics, Intermediate and Advanced levels, each lesson ending with something that runs on a Jetson.*

AI Training is a hands-on course for learning how all of the above actually works. The notebooks run in JupyterLab on the 3090, built on the same PyTorch, Ultralytics, LeRobot and Hugging Face versions as the robot trainer.

- **Basics:** training loops, overfitting, tuning, CNNs, a live camera classifier
- **Intermediate:** object detection, language models (embeddings, a tiny GPT, LoRA fine-tuning, RAG), control (PID, IMU filters), and working like an ML engineer
- **Advanced:** reinforcement learning and sim-to-real, robot learning (LeRobot behavior cloning, SmolVLA), models on the edge (quantization, distillation), drones, generative models (diffusion, image LoRAs), edge AI in production, scaling up, and a portfolio project

The rule for every lesson is that it ends with something running on a Jetson — an ONNX export, a TensorRT engine, a model in Ollama, or a controller driving real motors.

**Use it for:**
- Learning AI by building, not only reading
- Understanding the techniques the rest of the lab automates
- A path from first model to robot learning on edge hardware

## Reliability

::HighlightGrid

::HighlightCard{icon="mdi:briefcase-clock" title="Durable Jobs"}
Benchmarks, evals, setup applies, downloads, crawls and embeds each run in their own Kubernetes Job, not in the web pod, so a deploy doesn't stop them. Progress is saved to Postgres every 2 seconds, per-box locks are enforced by a unique index, and if a job's pod dies the box is put back — loaded models, services, keepalive pin — before the lock is released.
::

::HighlightCard{icon="mdi:backup-restore" title="Verified Backups"}
A nightly CronJob dumps every Postgres database to a different machine. A backup only counts once it's been restored: each run loads every dump into a throwaway Postgres, compares tables and row counts with the live database, and checks every graph still answers Cypher.
::

::HighlightCard{icon="mdi:memory" title="Jetson Memory Guards"}
Long, varied prompts grow Ollama's memory on a Jetson until the box runs out. Grading reloads the model when free memory drops below 1.5 GB, chat and API calls are refused below 1 GB rather than crash the box, and a model too big for a box is refused before anything is unloaded.
::

## System Architecture

Kingdom Tools runs as a single FastAPI pod in the `kingdom-tools` namespace, exposed via NodePort 30800. The reconciliation controller runs as a background thread in the same process, watching `KingdomService` CRs via the Kubernetes watch API.

The pod uses an in-cluster ServiceAccount with a ClusterRole scoped to read pods/services/nodes, patch deployments, manage secrets, and full CRUD on the `kingdomservices` custom resource and its status subresource.

The backend connects to nine data layers (PostgreSQL, MongoDB, MinIO, Redis, Weaviate, OpenSearch, Kafka, Temporal, ClickHouse) plus Grafana, Prometheus, and Loki for observability, and Gitea for container registry integration. The frontend is vanilla JS and CSS with no build step.

The AI side reaches out from the cluster: a small device agent on each Jetson exposes service control and metrics, short-lived privileged pods pinned to a node handle cache drops and disk scans, and long work runs as Kubernetes Jobs that copy the web pod's image, env and service account. Training, distillation and the robot trainer run in Docker containers on the RTX 3090 PC, sharing one queue so only one job holds the GPU at a time.

## Challenges Solved

::ChallengeGrid

::ChallengeCard{title="Imperative Infrastructure Management"}

#problem
Creating a new service meant manually provisioning resources across multiple systems, assembling connection strings, and writing deployment YAML — with no record of what belongs to what and no way to detect when things drift.

#solution
The KingdomService CRD makes infrastructure declarative. One YAML file defines what a service needs. The controller provisions everything, updates status with per-resource conditions, and continuously reconciles. `kubectl get ks` shows the health of every service.

::

::ChallengeCard{title="Orphaned Resources After Service Removal"}

#problem
Deleting a deployment didn't clean up its database, bucket, search index, event topic, or vector collection. Over time, orphaned resources accumulated across nine data layers with no way to trace them back to their original service.

#solution
The audit engine scans all nine data layers and cross-references against the service catalog. Resources not claimed by any registered service are flagged as orphans. The reconciler can fix missing resources, and finalizers on the CRD handle deletion cleanup.

::

::ChallengeCard{title="Secret Sprawl and Rotation"}

#problem
Each service needed manually generated secrets hardcoded into deployment manifests. No rotation, no central management, no way to audit which services had which keys.

#solution
Kingdom Tools generates cryptographically secure K8s Secrets per service, labeled for ownership tracking. Individual keys can be rotated from the dashboard without redeploying. The secrets are stored natively in Kubernetes, not in application config.

::

::ChallengeCard{title="No Per-Service Observability"}

#problem
Grafana dashboards had to be manually created for each service, with Prometheus queries hand-written to match the right namespace and pod patterns.

#solution
One-click dashboard creation generates seven-panel Grafana dashboards scoped to the service's namespace and pod labels. Request rate, error rate, latency, resource usage, and logs — all wired up automatically and tagged for easy filtering.

::

::ChallengeCard{title="Managing Edge AI Boxes by Hand"}

#problem
Every model change on a Jetson meant an ssh session: pull, load, check memory, restart a service, hope it fit. Nothing recorded which model worked at which quant and context, and one oversized load could take a box down.

#solution
The Devices page, model shelves and the model sweep turn that into a few clicks backed by data. Pulls are scored against each box's memory and disk, loads that can't fit are refused up front, and benchmark and sweep results show what actually runs well where.

::

::ChallengeCard{title="Deploys Killing Long Experiments"}

#problem
Every push to main restarts the web pod. Benchmarks, evals and crawls that ran inside it died with it, often leaving a Jetson with the wrong models loaded and its keepalive paused.

#solution
Durable jobs run each task in its own Kubernetes Job with state in Postgres. The UI keeps polling through a restart, and if a job's pod dies the web pod restores the box to how it found it before releasing the lock.

::

::ChallengeCard{title="Is the Fine-Tune Actually Better?"}

#problem
Training a LoRA is easy; knowing whether it beats the base model, at which quant, on which box, is not. Runs lost their context once their dataset changed or was deleted.

#solution
The LoRA Lab scores base against adapter on each dataset's own test questions, across quants on any Jetson. Model Records keep each run's dataset fingerprint, settings, deployment and score, so results stay comparable long after the data moves.

::
