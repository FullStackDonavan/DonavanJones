## Engineering Overview

**Where it started:**
The first version, built in 2025, replaced a spreadsheet-and-email enrollment process for small businesses. Each enrollment used to take 5–10 support emails and about 10 tracking spreadsheets, and applications were assembled by hand as PDFs.

**Where it is now (November 2026):**
The platform now runs the whole operation. Agents sell and enroll through it, premiums are billed and settled through it, commissions are calculated in it, and carriers and TPAs get their data from it. Current production numbers:

- **10,588** user accounts, including **1,859** licensed insurance agents
- **8,490** enrollment applications: **7,073** signed and **4,654** active paid policies
- **$10.8M** across **9,632** successful premium payments since in-app billing went live in July 2026
- **2,880** dependents covered across enrollments
- **15,706** generated application PDFs and **47,800** audit-trail entries
- **2,659** support tickets handled in-app
- **1,888** agent contracting submissions
- **83** group quotes covering **758** census employees in the underwriting pipeline
- About **2,000** users log in each month and about **200** each day

I am the sole architect and lead developer. I gather requirements directly from leadership and operations, present architecture tradeoffs to non-technical stakeholders, and own everything from schema design to production incidents. The codebase is about **180,000 lines** across **788 commits**, with **245 additive database migrations** and **95 test files**.

The hard engineering problems are no longer form handling. They are money movement that has to reconcile to the cent, sensitive data that has to stay encrypted, carrier file formats that have to be exactly right, and multi-role workflows where agents, admins, business owners, and employees all touch the same records.

## Technical Highlights

::HighlightGrid

::HighlightCard{icon="mdi:cash-sync" title="Card + ACH Billing With Recurring Charges"}
Premiums are collected by card or ACH through ePayPolicy. A card or bank token is reused for recurring billing only after it has gone through one successful charge. Daily cron jobs run recurring charges, poll ePayPolicy for status, and check ACH settlement. Charge locks and in-flight markers stop a payment from being taken twice when requests run at the same time. Failed payments start a cancellation workflow, and refunds are recorded as their own rows that link back to the original charge.
::

::HighlightCard{icon="mdi:file-sign" title="Signed PDFs, Encrypted at Rest"}
Each application, payment authorization, company agreement, contracting packet, and direct-deposit form is generated on the server with pdf-lib, with the captured signature drawn into the document. The 15,706 PDFs live in S3 and can only be opened through short-lived signed URLs. SSNs, bank accounts, and underwriting answers are encrypted at the field level. Admin views show masked values, and revealing a full value requires an explicit, audit-logged action.
::

::HighlightCard{icon="mdi:swap-horizontal" title="Carrier & TPA Data Feeds"}
Enrollment data goes out in the format each partner needs. Marpai gets 834 EDI files over SFTP on a three-times-a-week schedule, with plan-code mapping and per-member overrides. IHQ gets an export every 15 minutes. Other carriers get Excel workbooks through Microsoft Graph and Google Sheets. A reconciliation layer flags members whose status doesn't match between the platform and what the carrier received.
::

::HighlightCard{icon="mdi:account-network" title="Agent Hierarchy & Commission Engine"}
1,859 agents sit in an upline tree with agent admins and agency principals. Commissions are calculated from configurable rules, with dual-role handling, overrides, and changes to commissionable values. The system produces statement PDFs, range exports, and point-in-time snapshots. Leaderboards, team leaderboards, and bonus contests read from the same sales data.
::

::HighlightCard{icon="mdi:office-building-cog" title="Group Quoting & Underwriting Pipeline"}
A group quote moves through set stages: census pending, claims data, IHQ underwriting, proposal ready, payment, and conversion. Census data can come from an upload or from a tokenized assist link sent to the employer. Proposals and underwriting packages are generated automatically. When a group is sold, it converts directly into a live company with employees ready to enroll. So far 83 groups covering 758 employees have gone through this pipeline.
::

::HighlightCard{icon="mdi:history" title="Audit Trail & Operational Tooling"}
47,800 append-only audit entries cover enrollment, payments, and admin actions. Admins can impersonate a user, with the session recorded, to support them. Other tools include bulk agent import, paper-application import, coverage changes, effective-date management, and an in-app support desk with departments, attachments, and threaded messages (2,659 tickets so far).
::

## System Architecture

Business Benefit Alliance is a Nuxt 3 app deployed on Vercel. A single Nitro API layer (686 endpoints) serves six role-scoped surfaces. PostgreSQL through Prisma is the source of truth (93 models, 245 additive migrations). S3 holds documents, Redis handles caching and coordination, and eight Vercel cron jobs run the scheduled work: ACH settlement, ePayPolicy polling, recurring charges, group-quote billing, the Marpai 834 feed, IHQ delivery, agent comp defaults, and AI video rendering.

## Challenges Solved

::ChallengeGrid

::ChallengeCard{title="Never Charging a Customer Twice"}

#problem
Recurring premium billing runs on cron jobs, while admins and customers can also start charges by hand. On serverless hosting, a retried request or two overlapping jobs could charge the same policy twice, and an ACH payment can come back as failed days after it looked successful.

#solution
Each policy carries a charge lock and an in-flight marker. These are set atomically before any call to the processor and cleared only when the result is recorded. A token is used for recurring billing only after a successful first charge. A separate daily settlement cron rechecks ACH payments until they clear, and payments that fail later start a cancellation flow instead of quietly leaving the policy active.

::

::ChallengeCard{title="Encrypting Sensitive Data Without Breaking Operations"}

#problem
SSNs, bank accounts, and underwriting answers were needed for carrier exports, manual payment processing, and admin review. Storing them in plaintext was not acceptable, but staff still had to be able to do their jobs.

#solution
These fields are encrypted at rest, and existing rows were migrated with backfill scripts. API responses only ever return masked values. Exports and the manual-processing PDF show masked data by default. Seeing a full value is a deliberate, per-record action that is written to the audit log, and manual-processing documents are deleted on a fixed retention schedule.

::

::ChallengeCard{title="Getting Carrier Files Exactly Right"}

#problem
Each carrier and TPA wants a different format: 834 EDI over SFTP, IHQ exports, or spreadsheets. One wrong plan code or one missed termination means a member can't use their coverage.

#solution
Each destination has its own generator with plan-code mapping tables and per-member override records. Every file sent is stored, along with its member rows. A reconciliation layer compares platform status with what the carrier received, and an attention queue lists mismatches so a person can review them before they turn into a claim problem.

::

::ChallengeCard{title="Commissions That Hold Up to Scrutiny"}

#problem
1,859 agents in an upline hierarchy are paid on every sale. Agents can hold two roles at once, rules change over time, and agents dispute their statements. Calculating commissions on the fly from current data would give a different answer every time someone looked.

#solution
Commission rules are versioned data, not code. Changes to commissionable values and manual overrides are separate audited records. Statements are produced from point-in-time snapshots, so a past period always shows the same result even after rules or the hierarchy change, and every number can be traced back to its source.

::

::ChallengeCard{title="Keeping Serverless Postgres Healthy at Scale"}

#problem
With about 200 daily and 2,000 monthly users on Vercel serverless functions, the app hit Postgres connection exhaustion several times. The causes included a role connection cap, a misconfigured compute setting, and a session write that wasn't awaited and left transactions sitting idle.

#solution
I diagnosed each incident from pg_stat_activity and pg_stat_statements instead of guessing, fixed the configuration, and made it a rule that every Prisma write is awaited on serverless. Schema changes are strictly additive (no drops, renames, or type changes) across 245 migrations, so a deploy never breaks a running function that is still on the previous schema.

::

::ChallengeCard{title="Six Roles, One API, No Data Leaks"}

#problem
App admins, agent admins, agents, company admins, employees, and virtual assistants all read and write overlapping data through the same 686 endpoints. A route guard alone would not stop someone from calling an endpoint directly.

#solution
Every handler resolves the caller's role and scope (their downline, their company, or only their own records) before it builds a query. The UI guards are there for convenience, not security. Impersonation lets support see exactly what a user sees, and every impersonated session is audited.

## Database Design

::HighlightGrid

::HighlightCard{icon="logos:postgresql" title="93-Model PostgreSQL Schema"}
The core tables cover users, agents, companies, employees, applications, dependents, and plans. Around them sit payments, payment-method changes, direct deposit, commission changes and overrides, group quotes with census, events, and enrollments, Marpai 834 files and members, TPA deliveries, support tickets, training, live events, and AI video projects.
::

::HighlightCard{icon="mdi:file-document-outline" title="Document & Audit Records"}
15,706 application PDF records point to S3 keys, and URLs are created when a document is requested, never stored. AuditTrail, PaymentAuthorizationAuditTrail, and snapshot-run tables are append-only and hold 47,800 workflow entries.
::

::HighlightCard{icon="mdi:state-machine" title="Explicit State Machines"}
Applications go draft → underwriting_complete → pdf_generated → signed → paid, with canceled and void as exits. Group quotes go census_pending → awaiting_claims_data → ihq_in_progress → in_underwriting → proposal_ready → awaiting_payment → closed. Status is a queryable column on the record, not something rebuilt from events.
::

::HighlightCard{icon="mdi:database-sync" title="Additive-Only Migrations"}
245 Prisma migrations. Columns are never dropped, renamed, or retyped, and derived values are computed in handlers instead of being stored. Backfill scripts handle data changes such as encryption rollouts and commission fixes as separate, re-runnable steps.
